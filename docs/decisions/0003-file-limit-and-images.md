# 0003：放宽 63 个文件上限，以及笔记图片的存放方式

- **状态**：闫博 2026-10-20 裁定
- **日期**：2026-10-20
- **关联**：[0035](../specs/0035-agent-writable-knowledge.md)（Approved，本记录不修改它）、0036（目录容量）、0037（笔记图片）
- **源码依据**：origin/main `41b83b5`（git archive 快照，只读）

## 背景：三个上限从哪来

| 上限 | 来源 | 性质 |
|---|---|---|
| 63 个文件 | `os/yanfs.h:28` `YAN_FS_MAX_FILES 63`；格式定义在 `docs/specs/0021-yanfs.md:31,34`：目录只占块 0，4096 B = 64 B 头 + 63 × 64 B 目录项。`os/yanfs.c:149` 格式化时把 63 写进 `entry_capacity`，`os/yanfs.c:318` 挂载时要求它恰好等于 63，否则 CORRUPT。Guest 把整块缓存在 `os/yanfs.h:83` `metadata[4096]`。 | 盘上格式 + 编译期常量 |
| 63 的连带数组 | `os/note_metadata.h:88-89`、`os/note_relations.h:57`、`os/search_terms_linear.h:69`、`os/search_terms_index.h:101`、`os/note_blocks.h:56`、`host/semantic_corpus.h:11`（Host 侧 `YAN_SEMANTIC_FILE_MAX 63`，`host/semantic_corpus.c:60` 拒绝 slot ≥ 63） | 每个服务按 63 开的静态数组 |
| 16 KB 单篇 | `os/editor.h:118` `YAN_EDITOR_CAPACITY 16384`（0023 整稿上限）；`os/note_metadata.h:43` `YAN_NOTE_CANDIDATE_BYTES 16384`；MCP 单条请求上限 `tools/mcp_protocol.h:7` `YAN_MCP_INPUT_MAX 16384u`；0035 的写入上限照编辑器取 16384 | 编译期常量；YanFS 本身不限单文件大小（`size_bytes` 是 u32） |
| 64 KiB 镜像 | **不是代码上限。**`README.md:66,77` 的示例命令用 `--blocks 16`（16 × 4096 B = 64 KiB），测试镜像也是 65536 B；`tools/yan_mkfs.c:38` 接受 1..4294967295 块 | 只是示例和测试默认值，建镜像时加大 `--blocks` 即可 |

请求里的猜测「单个根目录 + metadata[4096] 目录缓存」是对的：盘上只有一块目录，Guest 正好缓存这一块。

## 两条路对比

路 A：多块目录。路 B：子目录。

| 影响面 | A：多块目录 | B：子目录 |
|---|---|---|
| 镜像格式、版本号 | 新增 version 2：头里用一个保留字段记录目录块数 D，目录占块 0..D-1，数据从块 D 开始，`entry_capacity = 64·D − 1`，CRC 覆盖整个目录区。v1 的字节布局不变 | 也要 version 2：目录项要加类型位和父目录，子目录本身要占 extent 或单独块；还要有路径解析 |
| 已有镜像迁移 | v1 照常挂载（就是 D=1）；需要更多文件时离线复制到新的 v2 镜像（保留 slot 号，连同 `.assets/` 一起复制），原镜像不动 | 同样离线复制；但旧文件都在根目录，用户还得自己决定怎么分目录 |
| `[[NAME#ID]]` 文件名写法 | **不变** | 要支持 `dir/NAME`：要改 0032 的引用语法、0027 的 `link:`、0021/0024 的名称规则、0033/0035 的 schema（`maxLength:31`），还有终端里所有带文件名的命令 |
| 0035 的锁、库身份 | 锁不变（仍按镜像文件加锁）。身份计算不变（0030 按 slot、名称、大小计算，`host/semantic_corpus.c:26-38`）；v1 镜像身份不变；迁移工具保留 slot 号，迁移后身份也不变（按 0030 公式验证），已建索引仍然有效 | 锁不变；身份要把路径算进去，0030/0033 的身份格式要改版，旧索引全部失效 |
| Guest metadata 缓存与内存 | 缓存从 4 KiB 增加到 D × 4 KiB（D=16 时 64 KiB，D=32 时 128 KiB）。各服务按 63 开的数组改为按实际容量从 arena 分配，每文件约 246 B（逐项见 0036）：1023 个文件约 +231 KiB，2047 个约 +477 KiB | 每层目录都要缓存或按需读取；路径栈、当前目录状态，还要处理遍历顺序 |
| 实现量 | 中等偏小：yanfs.c 的格式、校验、slot 循环改为按 D 参数化；mkfs 加一个参数；新增一个离线迁移工具；把常量改大 | 大：FS 核心、名称语法、六份以上已有 spec、终端命令、MCP schema 都要改 |

**可在线增长**（目录满了就自动扩块）没有选：目录后面紧接着就是数据 extent，要扩块就得在线搬动数据，这需要断电恢复，而 0021 明确不做。所以 A 的做法是 mkfs 时定好 D，以后要扩就离线迁移。

## 裁定（闫博 2026-10-20）

1. 采用多块目录（路 A），块数在 mkfs 时确定。
2. 默认上限 1023 个文件（16 块目录），不用 255；文件数做成 mkfs 参数（`--files`），可以调整。硬上限 2047（D=32），这是策略上限（2 的幂，目录 128 KiB）：数组按容量计入后五个 context 合计 1 988 720 B，留约 106 KiB 余量；预算本身最多能容纳约 2623 个，但余量只剩约 9 KiB。逐项计算见 0036「代码核实」；内存按 mkfs 时的实际容量从一次性 arena 分配，不按硬上限。
3. 旧镜像继续可用，支持离线迁移，迁移后库身份不变。
4. 图片从启动时指定的导入目录复制进来。
5. 单张图片上限 1 MiB。
6. 新增 `images NAME` 命令，`links` 的行为保持不变。

## 当时的推荐理由（已被采纳）

1. 引用语法、名称规则、MCP schema 都不用动；0032–0035 已经批准的行为原样保留。
2. 0035 的锁和库身份不受影响，v1 镜像的身份不变；迁移保留 slot 号，身份也不变。
3. 改动集中在 YanFS 的格式层，以及与文件数相关的数组改为按容量分配。
4. v1 镜像不迁移也能继续用；迁移是离线复制，原镜像不改。
5. 子目录主要解决「分类」，而现有的标签、链接和两个镜像已经可以分类。

## 图片：存放位置和流程（详见 0037）

- 图片文件放在 Host 上，**跟着各自的镜像走**：`notes.img` 的图片放在 `notes.img.assets/img/`，`learning.img` 的放在 `learning.img.assets/img/`（路径是 `realpath(image)` 加 `.assets/img/`）。两个镜像各管各的，和 0035 一样不跨镜像解析。
- 每个镜像里有一个 YanFS 文本文件 `img.index`，每张已登记的图片一行：`名称 字节数 sha256`。Guest 看不到 Host 上的目录，只能靠这个文件判断图片在不在：引用的名称不在 `img.index` 里，就显示 DANGLING。
- `img.index` 在 YanFS 里，所以 0035 的整库身份自然把图片登记也算进去；图片字节由清单里的 sha256 校验。
- 写入：一个 Host 写工具，拿和 0035 相同的锁，先原子地把图片复制进 assets 目录，再用 0035 的原子替换更新 `img.index`；同样有 `dry_run` 和 `expected_source`。
- 读取：一个只读 MCP 工具返回 MCP image 内容，读出的字节必须与清单里的 sha256 一致。

## 拆分

拆成两份：**0036 目录容量**和 **0037 笔记图片**。理由：

1. 层次不同：0036 改盘上格式和 Guest 内存；0037 只在 Host/MCP 上加功能，Guest 只多一个只读命令。
2. 风险不同：格式改动要做迁移和兼容验证，图片要做 Host 文件安全和 MCP 内容验证，混在一起会让 PR 超过约 400 行，审查也不好聚焦。
3. 依赖不同：0037 依赖 0035 的写路径已实现；0036 不依赖 0035。`img.index` 只占一个 slot，所以两份可以按任意顺序合入。

## 后果

- 0021 新增 v2 格式说明；`yan_mkfs` 新增 `--files`（缺省 1023）；Guest 新增一次性 arena，`yan_run` 检查 arena 不与环形缓冲区重叠；新增离线迁移工具。按容量计，Guest 内存在 1023 个文件时增加约 231 KiB，在 2047 个文件时增加约 477 KiB（逐项见 0036）。
- 图片方案：每个镜像旁多出一个 `.assets/` 目录，备份镜像时要连同它一起备份；每个镜像占用一个 slot 放 `img.index`。

## 追加裁定（闫博 2026-10-20）

- YanFS 文件硬上限现在就提到 4095（`YAN_FS_MAX_DIR_BLOCKS` = 64），取代上文的 2047；`--files` 缺省仍为 1023。
- 模拟器 RAM 定为 64 MiB，Guest 可用满 32 MiB（`__yan_arena_end = 0x80000000 + 32 MiB`），原「五个 context ≤ 2 MiB」预算由 0039 的 32 MiB 预算取代。
- 4095 下的 O(N²) 由 0040 处理；0040-P1 实测与 Q2（全库操作超 5×10⁷ 步时怎么办）仍待定。

## R7 迁移边界澄清（闫博 2026-10-21 批准）

- 盘上的语义索引在迁移后直接复用并保持 READY；0026 词项索引只在内存，新镜像上正常重建为 READY，再核对搜索内容、分数和排序一致。来源身份编码保持，见 0036-R7-AC1。
- 附件从 `realpath(OLD) + ".assets"` 递归复制普通文件和目录；符号链接、特殊文件使迁移失败，目标落在源附件树内时提前拒绝。迁移期间源镜像和附件须保持稳定，不新增快照或重试机制。
- 0035 的旁锁 `.lock` 保留。失败清理若又遭遇磁盘或权限错误，明确报失败并列出残留路径；断电恢复仍不在本阶段范围内。以上边界用于 R7 离线迁移。
