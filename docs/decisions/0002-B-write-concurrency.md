# 0002 B 写入的并发路线：镜像独占锁（BUSY），不走 Guest RPC

- 日期：2026-10-20　状态：**闫博 2026-10-20 裁定**　决策人：闫博　起草：develop-gpt
- 关联：[0001 路线 A→D→B](0001-roadmap-A-D-B.md)、[0035](../specs/0035-agent-writable-knowledge.md)

## 问题

B 要让 Agent 通过 MCP 写笔记。镜像同一时间可能被两类进程使用：`yan_run --disk-image`（Guest 终端）和 `yan_mcp`。需要决定由谁来写，以及两者怎样互斥。

## 代码里的现状（origin/main 41b83b5）

1. **Guest 和 Host 同时写，会真的写坏镜像。** `YanFs` 挂载后把目录块缓存在内存里（`os/yanfs.h`：`uint8_t metadata[4096]`）。0021 规定空闲空间每次都从「当前已验证目录」反推，覆盖时最后发布一个目录块。所以 Host 在 Guest 挂载期间新建一个文件后，Guest 下一次写入会做两件事：用旧的缓存目录发布，把 Host 那个文件从目录里抹掉；同时可能把 Host 刚占用的区间当成空闲区间分配出去。这不是读到旧数据那么简单，而是丢文件。
2. **现在没有任何互斥。** `tools/host_disk.c` 用 `fopen(path,"r+b")` 打开镜像，不加锁；0033 的只读工具靠「Guest 已退出、镜像稳定」这条前提和 STALE 检测兜底。只读时这样够用，写入时不够。
3. **Host 已经有完整的 YanFS 实现。** `os/yanfs.c` 是可移植 C，Host 侧已经编进 `yan_fs` 库（`yan_mkfs`、0033 的只读适配都在用），`yan_fs_create`、`yan_fs_replace` 现成可用。
4. **传输通道目前只有 Guest 发起的请求。** 0018 的块协议是 Guest 发请求、Host 回响应；Guest 是 UART 驱动的交互式终端，没有服务循环。`yan_mcp` 和 `yan_run` 是两个独立进程，没有进程间通道。
5. **镜像很小。** README 的例子是 `--blocks 16`（64 KiB），目录上限 63 个文件。

## 方案对比

| | 路线一：镜像独占锁，拿不到返回 BUSY | 路线二：Guest RPC，写操作交给运行中的 Guest |
|---|---|---|
| 做法 | `yan_run` 打开镜像期间持有排他锁；MCP 写工具每次调用时以非阻塞方式拿锁，拿不到返回 BUSY，零写入；拿到后用 Host 侧 YanFS 写 | 新增 Host→Guest 请求帧和 Guest 服务任务；`yan_mcp` 经新的进程间通道连到 `yan_run`，由 Guest 的 YanFS 写入 |
| 同写风险 | 由锁排除：任何时刻只有一个进程打开镜像写 | 由单写者排除：只有 Guest 写 |
| 实现量 | 小：锁约几十行（两个入口），Host 写适配和两个工具约 300–500 行，复用 `yan_fs` | 大：新协议规格（0018 量级）、Guest 服务任务和调度、IPC、`yan_mcp` 改为客户端、帧解析，估计是路线一的 5–10 倍 |
| 可测性 | Host 原生测试即可覆盖锁冲突、STALE、故障注入；加一个 Guest/Host 同镜像验收 | 需要 Guest 测试、IPC、超时、Guest 崩溃等组合场景；只有组合测试才能发现问题（M2a 的 F1 死锁就是先例） |
| 对学习工具的影响 | 闫博开着 Guest 终端时，Agent 写不进去（BUSY），要先退出终端；出题、读原文这些只读操作不受影响 | 闫博在终端里时 Agent 也能写，体验最顺 |
| 失败时 | 进程死掉，内核自动释放锁，不会留下死锁；写入可以做成整份镜像原子替换，失败时旧镜像原样保留 | Guest 卡住或崩溃时，RPC 要处理超时，还要判断 Guest 的 YanFS 是否已 FAULTED；部分完成的写入状态更难说清 |
| 什么时候改选 | 实际使用中 BUSY 频繁到妨碍学习流程（例如闫博需要长时间开着终端，同时让 Agent 写） | 同上，且愿意为此投入一个新阶段 |

## 推荐

**路线一。** 理由：

1. 这个风险是实打实的（目录缓存会导致丢文件），锁正好对症地把它消掉；路线二同样能消掉，但代价高一个量级。
2. Host 侧的 YanFS 和只读适配都是现成的，路线一几乎只是加一层写适配，符合 AGENTS「新模块优先、必要适配」的规则。
3. 失败语义最简单：内核锁随进程自动释放；镜像只有 64 KiB 量级，可以先写临时副本、fsync 后 rename，一次写入要么完全生效、要么完全不生效（团队手册 §3 B 也要求原子写入）。
4. 对学习工具的代价可以接受：出题、核对、定位原文都是只读，不受影响；只有「把结论写回库里」需要闫博先退出 Guest 终端。如果实际用下来受不了，再单独立项走路线二，路线一的工具接口可以保持不变。
5. 测试可以主要放在 Host 原生层；0034 之后 Guest 测试也进了 CI，同镜像验收能在 CI 里跑。

## 裁定（闫博 2026-10-20）

1. 并发路线选路线一：加锁，Guest 终端开着时写入返回 BUSY；写入先写临时副本，fsync 后再 rename。
2. 按手册「先预览，再确认提交」：增加只读预览（0035 采用写工具的 `dry_run` 参数），提交必须带预览时拿到的库身份，对不上就拒绝；`--allow-write` 保持默认关闭。
3. 身份用整个库的身份；单次写入上限 16384 字节。
4. 实施前先实测 `/mnt/e` 上两个进程间的 flock 能否互斥（两个镜像都要测）；任一不通过，两个镜像都要放在 WSL 原生文件系统里。
5. 学习笔记和普通笔记分开，放在两个镜像里。每个镜像由一个 `yan_mcp` 实例服务，锁和库身份各自独立（0035-R11）。

## 决策

采用路线一：以镜像旁的锁文件 `<image>.lock` 为锁对象（永不删除；顺序固定为先拿锁、再打开镜像，最后关闭、释放锁），用 `flock(LOCK_EX|LOCK_NB)`。`yan_run --disk-image` 在运行期间持有这把锁，拿不到就拒绝启动；MCP 写工具每次调用时拿锁，拿不到返回 BUSY。写入采用整份镜像「临时副本 → fsync → rename」的方式。0033 的只读工具行为不变。

## 后果

- 闫博开着 Guest 终端时，Agent 的写入会返回 BUSY；需要在学习流程里约定「先退出终端，再让 Agent 写回」。
- `yan_run` 要加一处锁逻辑（属于必要适配）。
- 实施前必须先在 WSL 的 `/mnt/e`（drvfs）上实测 flock 在两个 WSL 进程之间是否有效；如果无效，要求镜像放在 WSL 原生文件系统里（见 0035「前置条件」）。
